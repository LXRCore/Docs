## 2. Mistakes we learned from (and what we do instead)

### 2.1 Security is bolted on, not designed in
* **VORP** persisted client-sent health/stamina directly into the DB (issue #184, closed 2026-08) and had forgeable callback responses (issue #182: "responses never bound to source; shared sequential IDs make forgery trivial"). Its `addCurrency` still carries the comment `--add check for security`.
* **RSG** accepts `RSGCore:Server:SetMetaData(meta, data)` for *any* key — a client can set `isdead`, `injail`, `ishandcuffed`. Its `Kick()` has a `while true do … end` without a `Wait` on one path.
* **QBR / old LXR** exposed `AddItem`, `RemoveItem`, `GiveXp`, `SetLevel` as net events — the client decides what it owns.

**LXRCore:** there is no net event that changes money, items or XP; client-settable metadata is a whitelist; every callback answer is bound to the requesting source and request id; every net event is rate limited; failures are logged as exploit attempts with identifiers. Verified by `tests/test_events.lua`, `test_callbacks.lua`.

### 2.2 "Remove then add" inventory moves
qb/qbr/old-LXR inventories remove the item from the source, then add to the destination; when the add fails (weight, slot) the item is gone or duplicated (qb-core issues tagged *duplicat* / *dupe*). **LXRCore's** `Containers.Move` validates both sides — including swap feasibility — and only then mutates (`lxr-inventory/tests/run.lua`).

### 2.3 Name-keyed callbacks
RSG stores `ServerCallbacks[name]` and `ClientCallbacks[name] = cb` — two players (or two resources) calling the same callback at once overwrite each other. VORP got this right with unique ids; **LXRCore** uses unique ids in both directions, with timeouts and cleanup on disconnect.

### 2.4 Schema drift handled by hand
RSG checks for `weight`/`slots` columns at boot and `ALTER`s; VORP exposes `dbUpdateAddTables`; nobody records what was applied. Server owners cannot tell which version of the schema they run. **LXRCore** records every migration with a checksum and refuses to re-run changed files; resources register their own migrations through the core.

### 2.5 Framework-shaped monoliths
qb-derived cores bundle chat commands, vehicle spawning, paychecks, anti-cheat, Tebex, Discord logging and a NUI page into "core". The old LXRCore added 755 lines of anti-cheat, 611 of anti-dupe and 447 of Tebex to it. **LXRCore v3** core contains: identity, lifecycle, accounts, roles, permissions, RPC, items abstraction, database, logging. Everything else is a resource.

### 2.6 Steam-only identity (VORP)
`vorp_core` refuses to start without a Steam Web API key and keys everything by steam id. **LXRCore** keys by Rockstar license (always present), keeps every identifier, and re-links imported VORP rows on first login.

### 2.7 Polling
RSG hides player names with a `while true do Wait(5000)` loop, refreshes chat suggestions by iterating all commands per player, and depends on ox_lib's cache loop. VORP's client has three `Wait(0)` loops. **LXRCore** uses state bags, event-driven refresh and an adaptive prompt thread; the core is 0.00 ms idle.

### 2.8 No test, no truth
Every framework above documents behaviour it has never executed automatically; the qb-core tracker (200 closed issues) is dominated by `item`, `nil`, `error`, `vehicle`, `job` — exactly the categories a test suite catches. **LXRCore** ships 76 core tests + 7 inventory tests and marks anything not executed in-game as **NOT TESTED** in its docs.

### 2.9 Copy-the-API culture
RSG is qb-core with `QB` renamed; QBR is qb-core with `QB` renamed; the old LXRCore is QBR renamed. Same events, same weaknesses, same GPL obligations. **LXRCore v3** has its own vocabulary (`lxr:<domain>:<verb>` events, `LXR.Players.Get(src):AddMoney(...)`) and serves the foreign shapes only through a compatibility layer that can be switched off.

### 2.10 English-only, one language file at a time
RSG ships 33 locale files that drift (issues and commits are mostly translation fixes); VORP hard-codes strings in `translation/language.lua`. **LXRCore** has a locale engine with fallback, and the test suite fails if the Georgian mirror misses a key.

## 4. Where LXRCore goes further

1. **One engine, many faces.** RSG resources, VORP resources, QBR resources and native LXR resources run on the same server against the same player record (bridges + adapters, all documented with their limits).
2. **Money is auditable.** `lxr_ledger` answers "who gave whom what, from which resource" without a Discord webhook.
3. **Explicit character lifecycle.** Platform player → session → persistent character are separate concepts with serialised transitions.
4. **Installation is validated before it runs.** The recipe validator checks every repo/ref/manifest online; the previous recipe shipped with Markdown inside `server.cfg` and a wrong branch name.
5. **Honesty in docs.** Every capability is tested, NOT TESTED, or partial — never "works".

## 5. What is still missing (ours, not theirs)

* In-game validation on a real FXServer (no server on this machine).
* Official resources beyond the core chain are still QBR-derived and run through the compat layer.
* Weapon/ammo model (VORP's strongest area) is not designed yet; the vorp_inventory bridge says so.
* A HUD, appearance and banking resource on the native API.
